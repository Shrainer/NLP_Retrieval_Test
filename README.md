# Генерация кандидатов для каскадного ранжирования

## Идея решения

Решение построено как гибридный candidate-generation pipeline. Вместо одного универсального метода поиска используются несколько независимых источников кандидатов, после чего их ранжировки объединяются с помощью **Reciprocal Rank Fusion (RRF)**.

Один из сильных сигналов: локация. В тренировочном датасете, в который входят только positives, большая часть search_location_id и item_location_id совпадают.

Другой сильный сигнал: item_microcat_id. Найдя все оригинальные item_id, можно построить словарь микрокатегорий, используя params из benchmark_items — а в benchmark_queries без params можно их попытаться достроить на основе params из train. По моей оценке, больше 90% positives находятся в пуле, который можно получить по item_microcat_id. Несмотря на потенциал сигнала, в текущей реализации, скорее всего, используется не на полную. Мне не удалось выяснить, где этот сигнал будет давать большую полноту — как часть **RRF**, как **reranker** или что-то ещё.

Помимо этого, были замечены бессмысленные для генерации кандидатов данные — search_is_delivery (всегда 0) и search_category с item_category_id (всегда 114).

Финальный pipeline использует следующие источники:

1. **rule_fine** — объекты, которые встречались в `train.parquet` при совпадении нормализованного запроса и `search_location_id`.
2. **rule_coarse** — объекты, которые встречались с тем же нормализованным запросом независимо от города.
3. **bm25_local** — полнотекстовый BM25 по объектам текущего города.
4. **bm25_global** — полнотекстовый BM25 по всему каталогу.
5. **title_local** — отдельный BM25 только по названию объекта, ограниченный текущим городом.
6. **title_global** — BM25 только по названию объекта по всему каталогу.
7. **service_exact** — объекты с точно совпадающим нормализованным значением `Вид услуги` / `Тип услуги`, дополнительно ранжированные полнотекстовым BM25.
8. **bm25_microcat** — BM25 внутри узкого пула микрокатегории.
9. **query2query** — объекты, связанные с похожими историческими запросами из train.
10. **dense** — семантический поиск по `intfloat/multilingual-e5-small`.


Полнотекстовый индекс для BM25 строится по:

* `item_title_raw`;
* `item_description_raw`;
* `item_infm_params_text`.

Название объекта дополнительно повторяется **3 раза**, усиливая его вклад относительно длинного описания.

Помимо общего полнотекстового BM25 строится отдельный **title-only BM25**. Это позволяет сохранить независимый сигнал точного совпадения названия и не смешивать его полностью с описанием и параметрами.

## Локальный и глобальный BM25

Локальный BM25 ранжирует объекты непосредственно внутри пула текущего `search_location_id`.

Если локальный город содержит меньше `TOP_K` — то есть, 50 — объектов, локальный пул автоматически заменяется всем каталогом.

## Query-to-query retrieval

Для query2query строится BM25-индекс по уникальным нормализованным запросам из train. Для нового запроса выбираются до 20 наиболее похожих исторических запросов.

Объекты похожих запросов не сортируются по рейтингу. Вместо этого для каждого объекта накапливается вклад по всем похожим запросам:

```text
(score / max_score) / (20 + rank)
```

Таким образом, на итоговую позицию влияет как близость исторического запроса, так и его место среди найденных соседей.

## Dense retrieval

Для семантического поиска используется локальная модель:

```text
intfloat/multilingual-e5-small
```

Для item строится структурированное представление на основе:

* названия;
* значений услуги;
* отдельных полезных операционных параметров.

Для benchmark-запроса используются:

* `search_query`;
* значения `Вид услуги` / `Тип услуги`.

Полученные embedding-векторы нормализуются, после чего используется косинусная близость через скалярное произведение.
Item embeddings кешируются в:

```text
item_emb_e5small_v2_structured.npy
```

Имя cache-файла специально версионировано, поскольку представление item было изменено относительно более ранней версии pipeline.

## Microcategory

Microcategory pool строится из двух источников:

1. значений услуги в параметрах benchmark-запроса;
2. microcategory объектов, которые ранее встречались с тем же запросом в train.

Если доступны оба сигнала, сначала используется их пересечение. Если оно пустое, используется объединение.

Pool считается пригодным только в диапазоне:

```text
100 <= pool_size <= 40000
```

Отдельный microcat-BM25 запускается только для pool размером до 5000 объектов.

Это позволяет использовать microcategory как дополнительный сигнал, не превращая его в слишком широкий фильтр.

## Токенизация

Один и тот же tokenizer используется для BM25-индексов.

Обработка включает:

* приведение к lowercase;
* извлечение русских и латинских букв и цифр;
* лемматизацию обычных слов через `pymorphy3`;
* сохранение коротких alphanumeric-токенов, содержащих цифры.

## Два режима RRF

После построения всех candidate sources используется двухрежимная маршрутизация.

### `seen_location`

В этот режим попадает запрос, для которого одновременно выполняются условия:

* нормализованный `search_query` встречался в train;
* точная пара `(query, location)` также встречалась в train.

В этом режиме исторические rules считаются достаточно информативными и получают ненулевой вес.

### `general`

Сюда попадают все остальные запросы:

* известный запрос с новым location;
* полностью новый запрос.

В этом режиме rules отключены. Основной сигнал — локальный BM25, а остальные источники используются как дополнительные каналы восстановления и семантического покрытия.

## RRF

Для каждого источника используется его позиция в ranking.

Для объекта на позиции `rank` вклад равен:

```text
weight / (RRF_K + rank)
```

Вклады от всех источников суммируются.

Итоговое ранжирование сортируется по:

```text
(-rrf_score, item_id)
```

То есть при одинаковом RRF score используется лексикографический порядок `item_id`. Это делает финальный tie-breaking явным и повторяемым.

От каждого источника в fusion допускается до 1000 кандидатов.

## Padding

Если после fusion найдено меньше 50 объектов, кандидаты дополняются последовательно:

1. остатками глобального BM25;
2. остатками локального BM25;
3. детерминированным обходом корпуса по порядку `item_id` в исходном массиве.

Это позволяет получить корректный итоговый формат даже для запросов с малым количеством кандидатов.

## Кеширование

Для тяжёлых структур используются дисковые кеши:

* rule indices;
* полнотекстовый BM25;
* title-only BM25;
* query-to-query index;
* service/microcategory indices;
* dense embeddings.

Ключи кешей для train/items строятся на основе fingerprints входных данных, а имена индексов версионируются. Это позволяет не переиспользовать старый cache после изменения tokenizer или retrieval representation.

## Воспроизводимость

Pipeline не использует случайную выборку в runtime.

Основные rankings имеют явный tie-breaking, а итоговый RRF использует фиксированную сортировку по `(score, item_id)`. `solve.py` также удаляет возможные дубликаты и ограничивает ответ 50 объектами.

## Запуск

В каталоге с данными должны находиться:

```text
train.parquet
benchmark_queries.parquet
benchmark_items.parquet
```

Запуск:

```bash
python solve.py
```

При необходимости можно указать каталог с данными:

```bash
DATA_DIR=/path/to/data python solve.py
```

`solve.py` читает входные данные, строит context и последовательно генерирует до 50 кандидатов для каждого benchmark query.

На выходе создаётся:

```text
answer.csv
```

## Формат результата

Файл содержит две колонки:

```text
query_id,answer
```

`answer` — список `item_id`, разделённых пробелами, в порядке итогового ranking.

Перед сохранением `solve.py` проверяет:

* количество строк;
* уникальность `query_id`;
* максимальную длину ответа.

## Зависимости

Решение полностью локальное и не обращается к внешним API.

Используются:

* `pandas`;
* `numpy`;
* `pyarrow`;
* `bm25s`;
* `pymorphy3`;
* `sentence-transformers`;
* `torch`.

## Структура проекта

Минимальный состав runtime-файлов:

```text
core.py
solve.py
cache_utils.py
requirements.txt
train.parquet
benchmark_queries.parquet
benchmark_items.parquet
```

Дисковые pickle-кэши индексов являются только оптимизацией времени запуска и не требуются для воспроизведения решения. При отсутствии кэша индексы автоматически строятся из исходных parquet-файлов.
